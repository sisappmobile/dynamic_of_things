While implementing server-side pseudo_code execution (Option B) for BEO's detail form "Produk Transaksi" (c_custom_form id 2751043, header id 2749043), we hit and worked around a fundamental architectural constraint: **`Field.readOnly` lives on a single, per-COLUMN `Field`/`FieldCustomFormView` object shared across every row of a LIST-mode detail form — there is no per-row Field instance.** A pseudo_code/script `FOR element IN <table> ... element.<field>.readOnly = ... ENDFOR` loop over N>1 rows leaves only the LAST-processed row's value on the shared Field ("last row wins"), silently leaking one row's condition onto every other row's display.

**Why:** [dynamic-of-things-architecture.md](dynamic-of-things-architecture.md)'s detail-form model (both the Dart client `Template`/`Field` classes and the Java `HeaderForm.Template.valueOf`) was designed around one Field object per table column, not per cell — readOnly/mandatory are column-level JSON properties in the API contract, same on both `custom_dynamic_form.dart`/`PseudoCodeEngine.java` sides.

**How to apply — the pattern that works, confirmed by the user:**
1. Client-side: when a detail-row editor (`CustomDynamicFormDetailForm`) opens, the caller (`custom_dynamic_form_detail_list.dart`) scopes `headerForm.data[tableName]` down to a one-element array containing just that row (restored after the editor closes, committing on Save / discarding on Cancel). The editor also auto-fires a scoped `DynamicFormRefresh` the moment it opens (via its own locally-owned `DynamicFormBloc` instance, not `context.read` in `initState()` since that looks above the widget's own `build()`-returned tree) so the row's own readOnly/computed state is always freshly re-derived on open, self-healing any staleness left by an unrelated all-rows refresh.
2. Content-side: do NOT try to guard shared cross-row calculations (header totals like `total_diskon`/`subtotal_transaksi`/`total_transaksi`/`sisa_tagihan`) with an `IF <table>.size == 1` check if they live in the SAME pseudo_code as per-row readOnly toggles — that would break totals recomputation on the header-level "after save" refresh (which legitimately needs to scan all rows). The user's resolution: consolidate ALL the real logic (header field derivations like `status` from `DATEDIFF`, detail-row readOnly toggles, per-row value calcs, and cross-row totals) into ONE pseudo_code script attached to a single field, and put a dummy `BEGIN\nEND` pseudo_code on every OTHER field that needs to trigger a refresh (so `hasScript`/`field.hasOnChangeEvent` becomes true and its onChange dispatches `DynamicFormRefresh`) — the collector on both engines dedupes by exact script text and runs every distinct script found, so the one real script always executes regardless of which field triggered the refresh.

**DSL gotchas discovered along the way** (apply to both `json_script_engine.dart` and `dmsretail`'s `com.sisapp.helper.PseudoCodeEngine`/`PseudoCodeException` — keep any future engine fix in lockstep across both, or the two interpreters diverge):
- Plain `=` assignment does NOT evaluate comparison operators (`==`, `!=`, etc.) — only `IF`/`REQUIRE`/`ASSERT` conditions do. Use `IF cond ... element.x.readOnly = true ... ELSE ... ENDIF`, never `element.x.readOnly = a == b`.
- `element.<field>.readOnly = <bool>` (2 path segments after the loop var; also `mandatory`/`required`) is special-cased in `PseudoCodeEngine.setValue` (Java/online) to redirect the write into the FieldCustomFormView's readOnly/mandatory metadata directly, never touching the data tree. **This was NOT ported to `json_script_engine.dart` (Dart/offline) until 2026-07-21** — the offline engine originally had no such special case, so `element.item_price.readOnly = false` overwrote `element.item_price`'s own scalar value with `{"readOnly": false}` (or threw "Path error" if item_price already held a non-Map value), corrupting the data and crashing the next line that used `element.item_price` as a number (`NoSuchMethodError: Class '_Map' has no instance method '>'`). Fixed by porting the same special case into `_setValue` in `json_script_engine.dart`, redirecting matching writes into a top-level `_fields.<fieldName>.<readOnly|required>` sibling map — the same `_fields` convention `Template.loadTemplate` in `header_form.dart:290-304` already reads to set `Field.readOnly`/`Field.required`. Any future change to this special-casing must be applied to both engines or they diverge again.
- **Critical: `Formats.tryParseNumber` uses `NumberFormat("", "id").parse(...)` (id locale: "." = grouping separator, "," = decimal separator) for EVERY numeric string it's given — including strings that never came from user-typed, locale-formatted text.** Pseudo_code arithmetic (any division anywhere in a script forces Dart to produce a `double`) regularly yields values like `25000.0`. Before 2026-07-21, `Offlines.insertStatement`/`updateStatement`/the schedule-mirror insert+update/`buildKey`/`buildValue` all embedded such values into raw SQL via naive `"'${value}'"` string interpolation — Dart's default `double.toString()` keeps the literal ".0" suffix ("25000.0"), which then got stored verbatim in the SQLite TEXT column. The NEXT time that text was read back and passed through `Formats.tryParseNumber` (e.g. redisplaying the record, or the next pseudo_code refresh reloading the row), the id-locale parser misread the "." as a thousands-grouping mark and concatenated the digits — "25000.0" parsed back as **250000**, a silent, exact 10x inflation, on a field the user never touched. This is very likely what looked like "seluruh kolom numerik nolnya bertambah satu" when testing the BEO consolidated script (computed fields like `total_price`/`discount_nominal`/`sub_total_item`/`total_diskon`/`subtotal_transaksi`/`total_transaksi`/`sisa_tagihan` are exactly the ones that go through division in the script and therefore become doubles). Fixed by adding `Formats.numberToStorageString(num)` (whole numbers → no decimal point at all; genuine fractions → "," as the decimal separator, matching what the id-locale parser expects on read-back) and `Offlines.sqlLiteral(dynamic)` (routes `num` values through it, leaves everything else as `.toString()`), then using `sqlLiteral()` at every raw-SQL value-interpolation site in `offlines.dart`. Verified via a round-trip test against real pseudo_code-shaped values (25000.0, 40000.0, 25000.5, etc.) both through the fixed path and as a regression test proving the old naive path really did corrupt them 10x. **Any future code that writes a `num` into a raw SQL string in this file must go through `Offlines.sqlLiteral()`, not raw interpolation** — this is a systemic trap that will silently recur otherwise, since it doesn't crash or throw anywhere, it just quietly inflates the value on the next read.
- **FILE/FOTO/VIDEO/SIGNATURE/UPLOAD_* fields saved offline appeared empty on the next view/edit (found same 2026-07-21 session).** `Offlines.getSqlStatements` `jsonEncode()`s the `{name, mime, bytes}` attachment map before writing it to the SQLite TEXT column (so the raw stored value is a JSON *string*), but `Offlines.convert(value, fieldCustomFormView)` — the hook `FormContainer.convert()`/`hashDTOToMap()` both route every loaded field value through — had a no-op branch for these types that just returned the value unchanged. `DynamicForms.decodeValue` only reconstructs an `Attachment` when it receives a `Map` (`if (value is Map) {...} else { return null; }`), so a freshly-loaded String silently decoded to `null` — no exception, no log, the attachment just vanished. Fixed by having `Offlines.convert()` `jsonDecode()` the value back into a Map when it's a String for these field types (leaving it alone if it's already a Map, e.g. the in-progress-edit shape or an online JSON response). Verified via a full round-trip test (encode → jsonEncode → simulated SQLite text read-back → `Offlines.convert` → `decodeValue`) reconstructing the exact original bytes/name/mime, plus a regression test confirming the pre-fix path really did return `null`.
- **`f_dynamic_table_trigger`-driven INSERT/UPDATE/SELECT statements in `offlines.dart` threw `DatabaseException(incomplete input ...)` whenever a trigger action had zero CONDITION_EXTRA (or, elsewhere, zero CONDITION) rows (found same 2026-07-21 session).** 5 call sites built a `WHERE <clause>` by doing `dynamicTableTriggerActionDetailViews.isNotEmpty ? <filtered-and-joined clause> : "TRUE"` — but the `isNotEmpty` check was on the **whole unfiltered list** (which almost always has DATA/CONDITION rows and so is never empty), not on the specific `action_mode` subset (`CONDITION_EXTRA` or `CONDITION`) being joined. So whenever that specific subset was empty, the ternary still took the "build from the filtered list" branch, `.where(...).map(...).join(" ")` on an empty iterable produced `""`, and the final SQL ended with a bare `WHERE` — malformed, "incomplete input". Fixed by changing the condition to `.any((v) => v["action_mode"] == "<mode>")` (matching the exact predicate used in the subsequent `.where()`) instead of the unrelated `.isNotEmpty`, at all 5 occurrences (`handleTriggerActionInsert`'s CONDITION_EXTRA check, plus 4 CONDITION checks across the update/delete trigger-action handlers). Verified the exact WHERE-clause string this produces (`"TRUE"` instead of `""`) and that `WHERE TRUE` is valid SQLite syntax. Same file also has two OTHER latent risks in this exact trigger-handling code, found on follow-up review but only the first was requested to be fixed (2026-07-21): (1) - fixed - the `DATA` clause (INSERT's column list, UPDATE's `SET`) had no guard at all if zero `DATA` rows exist, which is also malformed SQL (`INSERT INTO tbl ( )` / bare `SET `) - unlike CONDITION_EXTRA there's no sensible "TRUE"-equivalent fallback for a column/assignment list, so `handleTriggerActionInsert`/`handleTriggerActionUpdate` now `return` early (skip the action) when `!dynamicTableTriggerActionDetailViews.any(action_mode == "DATA")`. (2) - NOT fixed, explicitly deferred by user - `buildKey`/`buildValue` do `variable[key][value]` without a null check; if a trigger variable's source-row lookup in `handleTrigger` finds no match, `variable[key]` is absent and this throws `NoSuchMethodError`. Also noted but not fixed: none of the raw-SQL-building code in this trigger system (`buildKey`/`buildValue`/insert/update/delete) escapes single quotes in interpolated values, so a text value containing an apostrophe will break the generated SQL - broad, systemic, not specific to triggers.
- **Second divergence found immediately after the above fix (same 2026-07-21 session), same root cause:** `PseudoCodeEngine`'s Java arithmetic AND comparison operators (`+ - * / > < >= <=`, unary `-`) all route every operand through `toBigDecimal`, which coerces `null` to zero — so e.g. `element.item_price > 500000` or `element.item_price * element.qty` on a field with no value yet (a brand-new detail row, before the user has typed anything — a routine case, not a script bug) evaluates against `0`, never throws. `json_script_engine.dart`'s `ExpressionParser` used Dart's native `+ - * /` operators directly on `dynamic`, and `_evalCondition` used native `> < >= <=`, both of which throw `NoSuchMethodError` on a null operand instead of coercing. Fixed by adding top-level `_toNumValue()` (null→0, mirrors `toBigDecimal`) and `_arithAdd()` (string-concat only when BOTH sides are strings, else numeric — mirrors `arithAdd`) helpers in `json_script_engine.dart`, and routing every arithmetic/comparison operator through them instead of Dart's native operators. Verified via throwaway `flutter test` against both an empty-row case (`x_1291043_produk_transaksi: [{}]`) and a realistic populated row. **Lesson: any future PseudoCodeEngine.java feature — not just readOnly/mandatory — needs an explicit check for "does json_script_engine.dart do the equivalent coercion/special-case," since the Java engine has accumulated defensive behavior the Dart one was never given a matching pass for.**
- CHECK-type fields round-trip as `"Y"`/`"N"` strings end-to-end (`DynamicForms.encodeValue` on the Flutter side, `DynamicFormHelper.mapToHashDTO` passthrough on the Java side) — comparing them against a `true`/`false` literal needs loose boolean coercion (`_looseEquals`/`equalsLoose`), otherwise `String == Boolean` is always false with no error, silently breaking the branch.
- `DynamicForms.encode()` used to mutate detail/sub-detail row Maps in place while building the wire-format request payload, corrupting live UI-bound data (e.g. a `bool` flipped to `"Y"` mid-edit) — fixed to deep-copy rows before encoding.
- A `/refresh` script/pseudo_code failure returns HTTP 202 (`GeneralResponse{RC:1, RM:"..."}`), not 4xx — `DotApis.dynamicFormRefresh()` used to silently return null on any non-200 status, swallowing the error with zero visible symptom. Fixed to throw with the server's `RM` message so it surfaces via the bloc's existing catch-and-toast/log path.
